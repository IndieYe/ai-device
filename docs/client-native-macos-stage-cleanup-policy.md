# stage 旧树清理策略

> 版本：1（2026-11-05）｜状态：策略已定并实现；真实 PKG 安装未实测

## 一、要清理的是什么

`commit_staged_program` 使用 `renamex_np(..., RENAME_SWAP)`，这是**交换**而不是移动。
提交成功后，旧程序树并不消失，它被换到 stage 路径上：

```
提交前    /opt/ai-device-client        旧树（正在被运行中的实例使用）
          /opt/ai-device-client-stage  新树（安装器刚写入）

提交后    /opt/ai-device-client        新树
          /opt/ai-device-client-stage  旧树   ← 本策略处理的对象
```

首次安装时目标不存在，走 `RENAME_EXCL`，stage 直接消失，**没有旧树，也就没有清理动作**。

## 二、清理什么、绝不清理什么

**删**：仅 `/opt/ai-device-client-stage` 这一棵被换下来的旧程序树。

**绝不删**（它们在提交时根本不在 stage 里）：

| 位置 | 内容 | 归属 |
|---|---|---|
| `~/Library/Application Support/ai-device-client/` | `client.json`、`token`、`state` | 指定用户 |
| `~/Library/Logs/ai-device-client/` | 运行日志 | 指定用户 |
| `~/Library/LaunchAgents/local.ai-device.client.plist` | 服务定义 | 指定用户 |
| `/Library/Application Support/ai-device-client-management/` | 管理锁、注册身份 | root |

这一点由布局决定，不是靠清理代码小心避让：程序树与配置/凭证/状态从不在同一路径下
（见 `client_macos_layout.py` 的 `PREFIX` 与 `directory`）。所以清理旧程序树**不涉及**用户数据。

## 三、执行时机与顺序

**只在实际发生交换之后清理**，且清理是提交之后的独立步骤：

```
1. 校验 stage（形状、owner、非重叠）
2. 一次 renamex_np            ← 这一步之后才存在"旧树"
3. 清理 stage 上的旧树         ← 仅当第 2 步返回成功
```

硬性约束：

1. **提交失败不清理。** 失败时 stage 上要么仍是**新树**（未交换），要么状态未知。
   误删会毁掉唯一一份已下载好的新程序，把"可通过重试修复"变成"必须重新下载"。
   因此清理只在 `PROGRAM_COMMIT_OK` 之后执行。
2. **未知状态不清理。** `PROGRAM_COMMIT_UNKNOWN` 既不能断言交换发生了，也不能断言没发生。
   两种可能下 stage 的内容含义不同，删除都可能毁掉可用数据，因此保留并报告。
3. **清理失败不影响安装结论。** 已提交就是已提交。清理失败只意味着磁盘上多留一棵旧树，
   不能让安装器把已经成功的提交报成失败——那会诱导用户重装，而重装会再交换一次。

## 四、清理的删除方式

不用 `rm -rf`，也不做"先删子项再删父目录"的多步删除：

- 先把 stage **整体重命名**到一个同目录下的临时名字（一次 `rename`，原子），
  这样运行路径与 stage 路径立刻都不再指向它，之后即使删除中断，也不会留下一个
  "看起来像 stage、内容却是一半旧树"的目录误导下一次安装。
- 再递归删除那个临时目录。
- 临时名带进程标识，避免与并发残留冲突。

失败时保留临时目录并报告路径，不静默吞掉。

## 五、为什么不在 postinstall 里删（当前实现的实际边界）

当前 `postinstall` **只做提交，不做清理**。这是有意的，原因如下：

1. **提交时可能仍有实例在使用旧树。** 升级链路里，旧实例的退出由协调器负责，
   而安装器的 `postinstall` 不知道协调器是否已经完成。此时删掉旧树，
   正在运行的实例会在下一次懒加载模块或读取 `runtime/` 下的文件时失败。
   这不是理论风险：解释器路径与 `sys.path` 都是绝对路径 `/opt/ai-device-client/...`，
   交换后路径已指向新树，实例继续运行会读到**新树**的文件——这一点本身就需要单独确认，
   而不是在清理这一步顺手处理。
2. **让包脚本承担"运行实例是否已退出"的判断，等于把停止证明塞进安装器。** 
   需求 §179 已经明确"服务已停止"目前只是调用方断言、无法由入口证明。
   清理策略不应绕过这个结论。

因此本策略只规定**清理的对象、时机与安全边界**，不把清理绑进 postinstall。
实际触发点有两个已具备的条件：

- 首次安装：无旧树，无需清理。
- 升级：由协调器在**确认旧实例已退出且新程序已就绪之后**执行清理（`blk-47951` 的升级链），
  那里已经持有完整的前置事实，不需要安装器猜测。

`commit-program` 子命令与 `cleanup` 子命令彼此独立（两者现在共用
`native/client-macos-program-verbs.h` 中的动词定义）：提交与清理是两个动作，
不合并成一个不可分割的副作用。

清理**没有** `--keep-old` 之类的开关，也没有任何生产调用方：当前只有独立二进制
可以直接触发 `cleanup`，协调器尚未接上该动作。在协调器接上之前，清理只是
一个有能力但也有风险的入口，不是一个已经运转的流程。

## 六、遗留

- **残留 debris 不会自动回收。** debris 名带 pid，因此不同次运行的清理互不阻塞；
  但也意味着中断留下的 `…stage.old-<pid>` 会一直累积，直到别的机制处理。
  这是已知限制，不是遗漏。
- 旧树被删除后，若新程序启动失败，**没有本地回退副本**。这符合需求"不自动回滚"，
  但意味着恢复路径是重装完整包。是否要保留一份短期可回退副本，属于产品取舍，当前不引入。
- 协调器**尚未接入** `cleanup`，因此“升级后自动清理”目前不成立；未来接入后的真实时序也未在实机验证。
- 并发安装器仍未排除：两个安装器可能各自拿到一棵 stage 树，清理只处理自己这次换下来的那棵。
- **路径安全修了三轮，每轮都只堵住一个写法，这是本任务最值得记录的教训。**

  | 轮次 | 做法 | 被什么绕过 |
  |---|---|---|
  | 1 | 字符串比较重叠 | `/opt/./x` 等别名（实测可删运行树） |
  | 2 | 原始路径 lstat 拒 symlink，再 realpath | `link/`：尾斜杠使 lstat 返回目标目录，symlink 检查失效（实测删目标，exit 0） |
  | 3 | 拒绝尾斜杠 | `link/.`：内核在穿过链接**之后**才解析 `.`，同样删目标（实测删目标，exit 0） |
  | 4 | 限定输入形状 + inode 绑定 | **中间分量为链接**（`/trusted/link/child`）：形态检查允许，无拼写规则可排除 |

  第四轮复核的结论是：**这个方向已经走到尽头**。前三轮都在给拼写建黑名单，第四轮发现根因不是语法
  —— 叶子是普通目录、但中间某段是链接，任何字符串检查都无法阻止内核穿越。

  另需记录一个本轮的事实性错误：我曾声称 `stage_cleanup_validate()` “返回被校验对象的 stat、不再重新
  lstat”，**这与代码不符**——`stage_cleanup_allowed` 只返回 bool，包装层不得不再次 `lstat`。审核指出后已修正注释，
  此处一并更正。

### 因此：清理入口已被禁用

`client-macos-commit-main.c` 的 `cleanup` 动词现在**无条件拒绝**（`STAGE_CLEANUP_DISABLED_V1`，rc 64），
不再调用 `cleanup_swapped_stage`。原语仍编译并在测试中被覆盖，但**没有可达的调用路径**。

理由：该入口接受两个 argv 路径字符串，无法证明第一个就是本次 commit 刚换下的旧树，也无法证明没有其他
实例仍需要它。在这种授权缺失下暴露“删除整棵程序树”的能力，风险高于收益。

重新启用需要的是协调器驱动的新设计（提交回执 + 旧树身份），**不是再来一轮拼写修补**。

输入形状检查仍然保留，但定位已降级为**输入卫生**，不是安全保证：
  - `path_spelling_plain()`：纯绝对路径，无尾斜杠、无空分量、任何位置不含 `.` / `..`；
  - 它只能拦住语法类误用，**拦不住中间链接**，也不能代替对象身份与生命周期证明。

启用前必须实现（审核列出的六项，缺一不可）：
  1. 时序与授权：只清理已确认成功且确实发生 swap 的旧树；UNKNOWN 不清理；确认旧实例不再需要它；
  2. 稳定对象与并发：受控父目录、可靠目录 fd、定义安装/发布/清理的串行化与锁所有权；
  3. 路径与对象校验：固定或受限位置、拒不安全拼写与意外链接、验证类型/owner/权限、保留防重叠检查；
  4. 删除边界：fd 相对遍历、拒绝跟随链接、明确挂载点与并发替换处理；
  5. 失败恢复：排他 debris 命名、防覆盖、部分删除可诊断、未知保留证据不盲目重试；
  6. 验证与文档：覆盖同名替换、父目录替换、别名、悬空链接、失败与真实安装生命周期。
