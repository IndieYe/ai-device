# P1 查询监督意图与候选验证恢复设计草案

状态：**仅设计，不授权恢复或新动作**。与 `native-helper-dispatch-handoff-design.md`、`native-lifecycle-implementation.md` 第246—253节及 `packages/device-runtime/native/HELPER.md` 一起使用；不得依据此草案删除已有意图或解除生产门禁。

## 当前事实与未封闭入口

私有 query-only 监督器在 daemon 双锁和 package EX 下发布不可覆盖意图后降为 SH；意图不自动退休，当前源码的若干入口在自身相应锁内检查。有两项实测边界：已持 package SH 时真实监督器在发布/验证前拒绝；注入降锁失败时可见意图保留且不验证或 fork。这些仅证明试验路径，不能证明掉电持久或旧参与者安全。

以下入口不能因上述检查而视为进程树受保护：

1. 历史 `publish_managed_helper_candidate` 在 package EX 下检查已有监督意图，然后 `publish_helper_candidate` 调用候选 Python 自检，但不为自检发布监督意图；隔离实验复现发布返回后后代存活、锁可取得（实施记录第255节）。当前新源码在复制/自检前默认拒绝受管发布，旧代码不自动修复。`read_helper_candidate`、部署和观察中的候选读取只校验文件，不调用此自检；须逐一按实际调用链区分。
2. `run_verified_helper_candidate` 的 `_verified_helper_bytes` 只读取和核验文件，不执行候选解释器；其后 `_verified_helper_modules` 会直接执行候选模块代码，后者可能派生子进程。当前新源码默认拒绝候选启动与候选 unit 部署，旧代码不自动修复。冻结代码不自动消费新意图，模块执行、服务启动和运行期子树之间没有已证明的完整原子监督与锁交接。
3. 普通 daemon 的新源码会检查意图，旧进程、旧 bootstrap 与旧快照不会自动更新；不能用当前源码的拒绝来推断存量环境安全。原生包钩子保守拒绝现有安装，但并非全部入口共同参与的锁协议。
4. 监督进程 SIGKILL 后，本地 subreaper 不再收养后代；本地 ECHILD、锁空闲、单个 pidfd 退出和守护进程 endpoint 消失均不证明后代及外部 systemd job 已终结。不能自动退休 unknown。

## 可实现前必须先完成的设计决策

- **统一覆盖表**：逐个枚举所有会验证/导入候选、写候选和 unit、启动 daemon、部署、更新、恢复、退休或卸载的实际入口及冻结快照；为每项记录使用的锁序、是否产生本地子进程或外部 systemd job、是否可能执行旧代码、只读观察与持久写入的区别。不可把查账入口误标为写入，或让旧入口靠新调用方一次性检查冒充已封闭。
- **监督单元及交接**：明确启动者、监督者、验证进程、服务 handler、每个 guard 及可委派的外部任务身份和责任。必须定义持有 daemon/package 锁与服务生命周期的连续性，防止验证→启动之间无锁间隙；旧候选自行加同一 flock 时不能简单重复获取以为安全。若无法证明完整交接，保持拒绝，不通过释放锁或删除 intent 跳过。
- **代际与绑定**：新操作使用不可覆盖的唯一 run ID、精确快照摘要、稳定 registry 标识及协议版本；root/管理员维护窗口保证 registry、必要祖先和挂载不被替换。具体身份、包版本及任务绑定按实际协议定义，不能用 PID、单一 inode 或锁空闲作为代际证明。
- **本地及外部树的证据来源**：候选必须说明怎样可靠覆盖验证导入、handler、其所有后代以及 systemd 可能派生的外部 unit/job；仅本地 subreaper 不够。cgroup 或 systemd 若被采用，须先证明所属范围、关闭新任务准入、成员/任务观察稳定性、宿主重启及权限、竞态与失败语义；不能把理论 cgroup 空置当作现有实现或跨重启证明。
- **终态与持久化**：候选协议应区分发布中、已发布/未知、运行中、停止中、已证明收口、明确不可恢复等状态；不可覆盖原 intent，终态要绑定 run ID 和证据摘要。文件 fsync、no-replace 发布及目录 fsync 的顺序、崩溃和错误/结果未知均要具体化，明确什么时点才可依赖 durable 证据；可见文件不是独立持久证明。状态转移必须有锁内再检查和确定的重复调用语义，不把状态名当证明。
- **管理员只读诊断与显式处置**：先提供不重放、无清理副作用的诊断，展示可验证事实、证据缺失和哪些入口仍运行旧版本；不得包含敏感数据。是否允许基于可验证证据提交退休记录、人工维护窗口下如何确认旧进程与外部 job 收口、宿主重启后如何处理，都必须定义为独立契约并测试。手工确认或锁空闲本身不是程序可证明的终态；缺证据保持 unknown，不删除 intent。
- **可用性和失败**：锁非阻塞失败、无限等待、进程不可中断、目录 fsync 失败、目录漂移、旧代码重启、systemd 排队和取消失败均明确 fail-closed 的诊断和运维路径。无凭据敏感日志；不把未知问题升级为清理、杀进程或自动重试。

## 后续验证门禁

1. 为上述覆盖表中的每个入口及旧版本提供能复现的锁内交错与无副作用测试，包含意图发布前后、降锁失败、检查后退出及旧入口重新进入；只读观察不得误触发业务动作。
2. 使用一次性隔离 Linux/systemd 环境验证真实进程树及外部 job，分别注入验证子进程派生后代、handler 和监督者死亡、父先退出、超时、宿主重启模拟及所有写入/目录 fsync 失败；按具体证据证明未知时仍拒绝，不得将单一 fault 模拟称为掉电证明。
3. 新旧冻结快照和存量迁移使用管理员维护窗口，先停旧入口并确认旧进程、job 和事务收口；旧记录手工处置需另行设计，不自动迁移或重建。真实服务、目标主机与远程发布另需授权。
4. 完整实现、跨入口回归和独立审查均通过，且仍在授权范围内，才可针对已证明的个别状态讨论受控退休；该草案和局部测试均不改变生产门禁。
