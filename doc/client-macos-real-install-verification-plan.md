## 0. 为什么需要这份方案

需求 §11 已明确：代码检查与 mock 不能代替制品验收。当前 macOS 阶段的实际情况是：

| 项目 | 数值 |
|---|---|
| native 源码 | 3142 行 |
| 相关测试 | 12178 行 |
| 离线测试通过 | 2037 passed / 20 skipped |
| **真实 PKG 安装次数** | **0** |
| **postinstall 执行次数** | **0** |
| **真实 launchctl 生命周期** | **0** |

所有“已实现”的判断都来自静态阅读与替身测试。四个独立评审轮次已反复指出，
测试数量不构成放行证据。因此下一阶段的唯一目标不是继续加代码，而是**取得第一次
真实执行反馈**。

## 1. 必须先解决的前提：本机不适合作为测试环境

### 1.1 已查证的冲突

只读探查当前机器（macOS 27.0.1 / arm64）的结果：

| 检查项 | 结果 |
|---|---|
| `/opt/ai-device-client` | 不存在 |
| `/Library/Application Support/ai-device-client-management` | 不存在 |
| GUI 域 `local.ai-device.client` | 未加载 |
| **`~/Library/LaunchAgents/com.device-runtime.macmini.plist`** | **存在，KeepAlive=true，RunAtLoad=true** |
| 其 ProgramArguments | `/Users/kongkongye/.device-runtime/instances/macmini/launchd/start.sh` |

这台机器上**已经有一个旧布局的 device 客户端常驻服务在运行**。

### 1.2 为什么不能就地测

- 需求 §3.2 明确“不自动部署当前开发机器”。
- 需求 §9 要求首次注册前检测旧服务定义与运行中的旧客户端，检测到就拒绝，不另启动第二个同身份客户端。也就是说，在本机安装新包会被**正确地拒绝**——这本身是需要验证的行为之一，但不能用来验证安装成功路径。
- 新包会写入全局路径 `/opt/ai-device-client` 与 `/Library/Application Support/...`，两者都是机器级单例，没有环境变量或安装前缀可以改（`managedPaths()` 硬编码，注释明确“No environment/console lookup, user-controlled install prefix”）。这意味着**无法通过改路径做实现在同机并行**。

### 1.3 结论

真实安装验证**必须在一台独立机器或一次性虚拟机中进行**，不能在本机打补丁式绕过。
这条不是保守，是代码结构决定的。

## 2. 测试环境要求

### 2.1 硬性条件

| 项 | 要求 | 理由 |
|---|---|---|
| 架构 | Apple Silicon arm64 | 需求只支持 arm64 |
| 系统版本 | 与构建时记录的 `minimum_system_version` 一致或更高 | 需求要求安装前拒绝不支持版本，需实测该拒绝 |
| 形态 | 一次性 VM，或可彻底擦除的独立物理机 | 见 §1 |
| 状态 | 无旧 `device-runtime` 服务、无 `/opt/ai-device-client`、无 `ai-device-client-management` | 否则首装路径测不干净 |
| 账户 | 至少一个普通非管理员 GUI 用户可以真实登录 | LaunchAgent 是 GUI 域，必须真的登录会话 |
| 权限 | 操作者具备 sudo，且**每次使用 sudo 需当次确认** | 见 §6 |
| 网络 | 可离线 | 验证“不联网装依赖”是验收项 |

### 2.2 明确不作为环境的东西

- **不**使用当前开发机。
- **不**使用 `ai-device-wt-macos-arms` 所对应的设备或工作树。
- **不**使用任何承载真实业务的机器。

### 2.3 快照策略

每个场景开始前恢复 VM 快照。这不是为了省事，而是因为安装验证会写入机器级单例路径，
失败后残留状态会污染下一个场景——而这正是本项目历史上多次误判的来源。

## 3. 被测制品

### 3.1 当前制品与源码不一致

现有 `build/client-native/mac-final-*` 目录下的制品**不包含本轮全部源码**。开始验证前必须：

1. 从当前 worktree 重新构建 tree / wheels / PKG
2. 记录每个制品的 SHA256
3. 在验证报告中写清“本次验证对应的 commit 与制品哈希”

用旧制品验证当前代码，等于什么都没验证。

### 3.2 需要先解除的一道门禁

当前 PKG 是 inspection-only：`PREINSTALL` 直接 `exit 1`，`Distribution.xml` 里
`installation-check` 调用 `rejectInspection()`。真实安装验证**必须**使用一个
允许安装的构建。

这带来一个必须先做的决定：

> 是否新增一个**专用的验证构建模式**（例如 `--verification` 参数），
> 使 PKG 可安装，但产物明确标记为非发布件？

建议**做**，理由：
- 直接改 inspection-only 常量会让“当前默认产物不可安装”这个安全属性消失；
- 专用模式可以把“允许安装”限定在显式参数下，默认行为不变；
- 需要在产物文件名、`Distribution.xml` 的描述、以及 `pkgutil --payload-files`
  可见的元数据里都带标记，避免验证包被误当发布包分发。

#### 与残留检测合并实施

真实发布版的 `preinstall` 本来就要重写（现在是 `exit 1`），所以**残留检测应作为
这次重写的一部分，不单独做**。先做一个能跑但装不了的 preinstall 再改一次，
是白折腾。

#### preinstall 的残留检测：用拒绝代替清理

**结论：cleanup 不做，改用「检测到 stage 残留就拒绝安装」。**

##### 为什么不用清理

cleanup 意味着再次回到四轮评审都未做对的运行时序控制（提交回执、旧树身份证明、
生命周期串行化）。而 `bom(5)` 已证明 Installer 不会清理 BOM 外的残留，
所以“路径唯一化 + 拒绝”与“路径唯一化 + 清理”对混树的有效性相同，前者简单得多。

##### 为什么拒绝不会锁死重装

关键在于：**第一次安装与 A→B 升级之后，stage 路径都是消失的**，因为
`RENAME_EXCL` 把整个目录移走了。

| 次序 | 装前 stage | commit | 装后 stage | 结果 |
|---|---|---|---|---|
| A→B 升级 | 不存在（路径不同） | `RENAME_EXCL` | 被移走，路径消失 | ✓ 可再次升级 |
| 同版第 1 次重装 | 不存在 | `RENAME_SWAP` | 旧树留回，脏 | ✓ 本次正常 |
| 同版第 2 次重装 | **脏** | — | — | **拒绝，不写 payload** |
| 人工删除后 | 不存在 | `RENAME_SWAP` | 旧树留回 | ✓ 回到上两行 |

因此拒绝只触发于“同版本第 2 次重装”——**恰好就是目前唯一会混树的场景**。
产品没有失去重装能力，只是需要人工介入一次。

##### 两个机制合起来没有死角

```
路径唯一化  → A→B 升级安全（路径不同）
残留检测    → 同版本反复重装安全（拒绝而非混树）
```

混树发生的必要条件（stage 同时含新 payload 与旧文件）在每一步都不可能成立。

##### 实现约束

1. **必须覆盖悬空符号链接。** `[ -e ]` 对悬空 symlink 返回 false：
   ```sh
   if [ -e "$STAGE" ] || [ -L "$STAGE" ]; then ... exit 1; fi
   ```
2. **位置必须在 preinstall。** postinstall 时 payload 已写入，无法区分“本来就在”
   和“刚写进去的”；preinstall 在写入前，能干净判断。
3. **错误信息要可操作**：给出具体路径、可能成因（同版本重装）、以及需要人工执行的命令。

##### 代价

同版本第 2 次重装需人工删一次目录，且需 sudo（目录属 root）。
比静默混树好得多：混树是无声错误，人工介入是明确失败。

##### cleanup 代码的去留

**保持禁用，不修复，不删除。** 现在的理由不是“不必要”，而是“有了更简单且
fail-closed 的替代”。删除需要单独授权。

##### 对验收口径的影响

C1（旧 stage 树被清除）仍为**未实现**，但**不再阻塞交付**——因为 C2 由
“路径唯一化 + 残留拒绝”共同满足。阶段结论不再因 C1 卡住。

这一项需与验证构建模式一起评审。

## 4. 验证场景

按需求 §11 的 25 项矩阵筛选出**只能在真实环境验证**的部分，按依赖顺序排列。
每项都要独立记录结果，不合并成“整体通过”。

### S1 — 干净机首次安装（未配置）

| 项 | 内容 |
|---|---|
| 前置 | 全新快照，无任何 ai-device 残留 |
| 操作 | `sudo installer -pkg <pkg> -target /` |
| 期望 | 安装成功；`/opt/ai-device-client` 存在且内容与 tree 清单一致；**不启动服务**；无配置时状态为“待配置”而非循环重启 |
| 关键核对 | postinstall 是否真的执行了 commit；`/opt/ai-device-client-stage` 的最终状态；`install-status` 文件内容 |
| 已知未验证点 | postinstall 从未执行过，本项是它第一次运行 |

### S2 — 首次配置

| 项 | 内容 |
|---|---|
| 操作 | 以指定普通用户身份完成配置（运行用户、身份、URL、凭证） |
| 期望 | LaunchAgent 加载；服务在**该普通用户**的 GUI 域运行；`ps -o user` 确认不是 root |
| 关键核对 | HOME 与 program 归属正确；凭证不进入 stdout/stderr/日志 |
| 对应验收 | §11「Mac root 安装程序」 |

### S3 — 生命周期

| 项 | 内容 |
|---|---|
| 操作 | 用户登出 → 重新登录；可选重启 |
| 期望 | 登出后服务停止；重新登录后启动；不要求未登录运行 |
| 关键核对 | `launchctl print gui/<uid>/local.ai-device.client` 在各阶段的状态 |

### S4 — 同版本重装

| 项 | 内容 |
|---|---|
| 操作 | 对已安装环境再次安装同版本包 |
| 期望 | 程序可修复；配置/身份/状态不变；不重复创建服务；不产生第二个实例 |
| 关键核对 | RENAME_SWAP 后 stage 的残留内容；debris 是否按设计处理 |

### S5 — A→B 升级（空闲）

| 项 | 内容 |
|---|---|
| 前置 | 在 A 版本上完成配置并确保实例空闲 |
| 操作 | 通过 Upgrade 入口执行 |
| 期望 | 版本实际变为 B；配置与日志保留；ready 精确匹配新的 build_id |
| 关键核对 | 阶段码输出；`AI_DEVICE_UPGRADE_READY_EXACT_V1` 是否出现 |

### S6 — 忙时拒绝升级

| 项 | 内容 |
|---|---|
| 前置 | 在前台或后台任务执行中触发升级 |
| 期望 | 拒绝升级；任务继续；新请求准入正常；不排队等待 |
| 关键核对 | 退出码与阶段码；任务未中断 |

### S7 — 忙拒绝后重试

| 项 | 内容 |
|---|---|
| 操作 | S6 之后，待任务结束再次升级 |
| 期望 | 同一路径可成功，不被旧意图永久阻塞 |

### S8 — 停止失败 / 状态未知

| 项 | 内容 |
|---|---|
| 操作 | 制造旧实例无法正常退出的情形（见 §5 故障注入） |
| 期望 | 不覆盖运行程序；不强杀；报告为 UNKNOWN 而非成功 |

### S9 — 损坏修复

| 项 | 内容 |
|---|---|
| 操作 | 破坏已安装的 `/opt/ai-device-client`（例如删掉入口或解释器） |
| 期望 | 无需执行旧升级器即可重装修复；确认服务不在运行后处理 |

### S10 — 普通卸载

| 项 | 内容 |
|---|---|
| 操作 | 按文档卸载 |
| 期望 | 服务移除；**配置与业务数据保留** |

### S11 — 错平台 / 损坏包

| 项 | 内容 |
|---|---|
| 操作 | 尝试安装 x86_64 包、篡改后的包、低于最低系统版本的包 |
| 期望 | 尽量在停机前拒绝；不改配置身份；错误信息明确 |

### S12 — 并发安装

| 项 | 内容 |
|---|---|
| 操作 | 两个 installer 同时执行（见 §5） |
| 期望 | 无双进程、无重复服务 |
| **当前预期** | **大概率失败** —— commit 明确不取管理锁，并发安装器互斥未实现 |

### S13 — 旧布局冲突

| 项 | 内容 |
|---|---|
| 前置 | 在测试机上故意创建 `com.device-runtime.macmini` 之类的旧服务定义 |
| 操作 | 尝试首次安装/注册 |
| 期望 | **拒绝**并给出明确说明；不覆盖；不启动第二个同身份客户端 |
| 备注 | 这一项可以在本机**只读地**验证拒绝分支，因为拒绝不产生副作用 |

### S14 — 中心 / MCP 回归

| 项 | 内容 |
|---|---|
| 期望 | 客户端清理不导致原部署/启动能力失效 |
| 备注 | 与 macOS 安装无强依赖，可与其他工作并行 |

## 5. 故障注入方式

只列**不改变生产代码**的手段。任何需要改代码才能注入的故障，单独提请评审。

| 目标 | 手段 |
|---|---|
| 旧实例不退出 | 让实例持有租约期间持续有任务；或临时把 ready 应答替换为不响应（需在隔离环境内） |
| 安装器中断 | 在 postinstall 执行中途 `kill -9` installer（此操作用 sudo，需当次确认） |
| 并发安装 | 同一终端并行起两个 `installer` 进程 |
| 损坏包 | 复制 PKG 后修改 BOM 或 payload 的一个字节 |
| 磁盘不足 | 挂载一个小容量 sparse image 作为目标（避免动真实磁盘） |
| 权限不足 | 用非管理员用户执行 installer |

**禁止**使用的手段：
- `pkill -f` 之类范围不可控的杀进程
- 删除或重建锁文件（无法证明旧 inode 持有者已退出）
- 对本机任何真实服务执行 stop/restart

## 6. 停止条件与安全边界

### 6.1 立即停止并报告的条件

- 任何一步影响了**当前开发机**上的 `com.device-runtime.macmini` 服务
- 出现无法用快照回滚的状态残留
- 需要超出已授权范围的 sudo 操作
- 测试机上有未知的其他客户端实例

### 6.2 sudo 使用规则

本方案涉及的所有 sudo 操作必须**逐条列给用户、获得当次确认后执行**。不接受
“验证期间整体授权 sudo”这种模糊形式。每次调用前说明：要执行什么、改哪个路径、
如何回滚。

### 6.3 不做什么

- 不 push、不部署、不操作任何真实服务
- 不删除任何临时目录、缓存、制品（沿用既有全保留要求）
- 不对中心/MCP 做变更

## 7. 证据要求

每个场景产出：

1. `version` / `build_id` / 制品 SHA256
2. 平台与系统版本
3. 实际执行的完整命令
4. 退出码与关键输出（**不含凭证**）
5. 关键路径的实际状态（`ls -la`、`launchctl print` 片段）
6. 结论：通过 / 失败 / 未得出
7. 未测项说明

证据存放在独立目录，命名带时间戳与场景编号，不复用旧制品名称。

## 8. 建议的执行顺序

不是按 S1…S14 顺序，而是按“能多快得到有效反馈”排序：

```
第一轮（最小可行）
  S1 首次安装        ← postinstall 第一次真跑，信息量最大
  S2 首次配置
  S3 生命周期
  ↓ 这一步就能暴露绝大多数问题

第二轮（升级路径）
  S5 A→B 升级
  S4 同版本重装
  S10 卸载

第三轮（失败与边界）
  S6 / S7 忙拒绝
  S8 停止失败
  S9 损坏修复
  S11 错平台

第四轮（已知缺口，预期失败）
  S12 并发安装       ← 大概率失败，用来确认缺口真实存在
  S13 旧布局冲突
```

先做第一轮。如果 S1 就失败（很可能，因为 postinstall 从没跑过），
后续场景全部无意义，应停下来修。

## 9. 验收口径：「未实现」与「不适用」

### 9.1 判定规则

> **「不适用」只用于验收要求本身不再成立**（需求取消、平台无此机制）。
> **「未实现」用于要求仍然成立、但当前没有可用实现。**

cleanup 属于后者，三条事实支撑：

1. **需求侧要求未取消。** §11 要求同版重装与 A→B 升级成立；固定共享 stage 路径若不清除，
   会与下次安装的 payload 混树。该风险至今**未被证伪**。
2. **用户授权的是换方案，不是取消能力。** 即从字符串路径修补改为协调器提交回执 ＋ 旧树身份证明
   ＋ 生命周期串行化。实现至今完整保留在原生语层。
3. **代码现状是主动禁用，不是不存在。** 生产入口返回 `STAGE_CLEANUP_DISABLED_V1` 和 rc64，
   原语与测试 harness 仍可直接调用。被主动关掉的功能是推迟，不是移除。

标「不适用」等于悄悄把验收范围缩小一格，而这正是本项目反复出问题的方式。

### 9.2 清理缺口：独立能力项

不把清理塞进各场景重复失败，抽成独立能力项：

| 项 | 内容 | 口径 |
|---|---|---|
| **C1** | 升级/重装后旧 stage 树被清除 | **未实现，且决定不做**。由“残留检测 + 拒绝安装”替代（§3.2） |
| **C2** | 旧树不清除时不污染下次 payload | **已由两个机制共同满足**：路径唯一化（已实施）+ 残留拒绝（待实施） |

同一缺口只记一次。否则它会在 S4、S5、S10 里各失败一遍，把 1 个缺口数成 3 个。

#### C2 的满足方式（已修正）

先前的口径是单靠 stage 路径唯一化，那是错的：同版本反复重装仍会混树。
正确组合是两个机制：

| 安装序列 | 由谁保证 | 结果 |
|---|---|---|
| A→B 升级 | 路径唯一化 | ✅ |
| 同版本第 1 次重装 | 路径唯一化（路径不存在） | ✅ |
| 同版本第 2 次重装 | **残留检测拒绝** | ✅ 不混树，但需人工清理后重试 |

因此 **C2 的满足以 §3.2 的残留拒绝实装为前提**。在 preinstall 落地前，
C2 仍为“部分满足”，阶段结论仍卡住。

依据：`bom(5)` 明确 Installer 根据 BOM 决定 install/remove/upgrade，BOM 外的
残留文件不会被打理。完整推导见
`doc/client-macos-stage-path-uniquification-plan.md` §3.3。

**因此 S4 必须按三连装设计**：第 3 次应被**拒绝**（而非混树）。
若第 3 次安装成功且 live 树多出旧文件，则是残留检测失效的信号。

### 9.3 各场景受影响情况

| 验收项 | 依赖残留检测 | 口径 |
|---|---|---|
| S10 卸载保留配置与业务数据 | 否（移除服务＋保留数据，独立路径） | **适用**，应实测通过 |
| S4 同版本重装 | 是 | **适用**；按三连装设计，第 3 次预期被**拒绝** |
| S5 A→B 升级 | 否（路径不同） | **适用**，应实测通过 |
| S12 并发安装 | 否（锁问题，另一缺口） | **适用**，预期**失败** |

关键区分：**S4/S5 本身要测、要跑**，不能因为任何缺口就跳过整个场景。
安装、启动、ready 行为可以正常验。

### 9.4 对阶段结论的影响

> **存在任何「未实现」项时，macOS 阶段结论只能是「未完成交付」，不能写「通过」或「基本通过」。**

但这个门槛现在有明确出路：

| 缺口 | 状态 | 是否阻塞交付 |
|---|---|---|
| C1 旧树被清除 | 未实现，**决定不做** | **不阻塞** —— 由残留拒绝替代 |
| C2 不污染下次 payload | 路径唯一化已做 + 残留拒绝待做 | **残留拒绝落地后不阻塞** |

因此：**C1 永远为“未实现”不再是障碍**，前提是 §3.2 的残留检测实际落地并被
真实验证。在它落地前，C2 仍为部分满足，阶段结论仍卡住。

不再需要为了 C1 去改需求或实现 cleanup。

### 9.5 其余预期失败项

以下项在现有代码下**预期不通过**，不应在验证后当作「新发现的 bug」：

| 项 | 预期失败原因 |
|---|---|
| S12 并发安装 | commit 不取管理锁，无并发互斥 |

### 9.5.1 已知缺口：per-pid stage 残留无回收

存在第二套 stage 机制，与 PKG 安装路径独立：

| | PKG 安装路径 | 原生安装器发布路径 |
|---|---|---|
| 入口 | postinstall → commit 动词 | `installer-inspection` 的 `upgrade-registered-program` / `repair-registered-program` |
| 发布函数 | `commit_staged_program` | `publish_first_program` / `publish_registered_target` |
| stage 路径 | `/opt/ai-device-client-stage`（固定） | `/opt/.ai-device-client-stage-<pid>`（per-pid） |
| 旧树去向 | 留回固定 stage | 留回 `.…-<pid>` |

**调用链已核实**：

```
publish_first_program ← first-entry.h:15 ← installer.m:19
publish_registered_target ← registered-upgrade.h:92 / repair-entry.h:163 ← installer.m:40
```

`installer.m:52-58` 的动词分派生效，且该二进制已编译进制品
（`.../expanded/Scripts/installer-inspection`）。

**准确表述**：这是**活的生产代码路径**，不是实验机制；当前仅被 inspection 门禁
（preinstall `exit 1`）挡住无法执行。上一版写成「未接入生产」是错的，已纠正。

**缺口内容**：`copyfile` 失败或校验失败时，`fail("...; stage retained")` 会保留
整棵 `.…-<pid>` 树。全仓搜索 `gc-stage` / `prune` / `stale stage` **零命中**，
没有任何回收机制。固定 stage 每版本留一个，而 per-pid 每次失败留一份完整体积，
量级不可预测。

**与本验证方案的关系（重要）**：

> 该路径与 inspection 门禁**直接相关**。§3.2 要求为验证准备可安装的构建——
> 一旦门禁解除，`installer-inspection` 及其动词分派即成为可达路径。

因此它不是「未来缺口」，而是**解除门禁后即暴露的当前缺口**。本验证方案不把它列入
S1–S14 场景（因为本次验证的主路径是 postinstall → commit），但必须在验证报告中
明确标注：“本次未覆盖 installer-inspection 的发布路径及其残留”。

**本机现状**：`/opt` 下无任何 ai-device 残留，基线干净。

**建议**：在 §3.2 的验证构建模式评审中，一并决定是否同时限制或禁用
`installer-inspection` 的 per-pid 发布路径，避免验证期间引入不可控的残留。

### 9.6 观察项：cleanup 禁用后的真实残留

### 9.6 观察项：cleanup 禁用后的真实残留

cleanup 禁用后，S4/S5 会**真实地**在磁盘上留下旧 stage 内容。这必须作为明确观察项

第一手材料——可能比任何静态评审结论都有用。

执行 S4/S5 后应记录：残留路径、文件数量、与本次 tree 清单的重叠情况。
