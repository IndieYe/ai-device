## 0. 为什么需要这份方案

需求 §11 已明确：代码检查与 mock 不能代替制品验收。当前 macOS 阶段的实际情况是：

| 项目 | 数值 |
|---|---|
| native 源码 | 3142 行 |
| 相关测试 | 12178 行 |
| 离线测试通过 | 2037 passed / 20 skipped |
| **真实 PKG 安装次数** | **0** |
| **postinstall 执行次数** | **0** |
| **真实 launchctl 生命周期** | **0** |

所有“已实现”的判断都来自静态阅读与替身测试。四个独立评审轮次已反复指出，
测试数量不构成放行证据。因此下一阶段的唯一目标不是继续加代码，而是**取得第一次
真实执行反馈**。

## 1. 必须先解决的前提：本机不适合作为测试环境

### 1.1 已查证的冲突

只读探查当前机器（macOS 27.0.1 / arm64）的结果：

| 检查项 | 结果 |
|---|---|
| `/opt/ai-device-client` | 不存在 |
| `/Library/Application Support/ai-device-client-management` | 不存在 |
| GUI 域 `local.ai-device.client` | 未加载 |
| **`~/Library/LaunchAgents/com.device-runtime.macmini.plist`** | **存在，KeepAlive=true，RunAtLoad=true** |
| 其 ProgramArguments | `/Users/<user>/.device-runtime/instances/macmini/launchd/start.sh` |

这台机器上**已经有一个旧布局的 device 客户端常驻服务在运行**。

### 1.2 为什么不能就地测

- 需求 §3.2 明确“不自动部署当前开发机器”。
- 需求 §9 要求首次注册前检测旧服务定义与运行中的旧客户端，检测到就拒绝，不另启动第二个同身份客户端。也就是说，在本机安装新包会被**正确地拒绝**——这本身是需要验证的行为之一，但不能用来验证安装成功路径。
- 新包会写入全局路径 `/opt/ai-device-client` 与 `/Library/Application Support/...`，两者都是机器级单例，没有环境变量或安装前缀可以改（`managedPaths()` 硬编码，注释明确“No environment/console lookup, user-controlled install prefix”）。这意味着**无法通过改路径做实现在同机并行**。

### 1.3 结论

真实安装验证**必须在一台独立机器或一次性虚拟机中进行**，不能在本机打补丁式绕过。
这条不是保守，是代码结构决定的。

## 2. 测试环境要求

### 2.1 硬性条件

| 项 | 要求 | 理由 |
|---|---|---|
| 架构 | Apple Silicon arm64 | 需求只支持 arm64 |
| 系统版本 | 与构建时记录的 `minimum_system_version` 一致或更高 | 需求要求安装前拒绝不支持版本，需实测该拒绝 |
| 形态 | 一次性 VM，或可彻底擦除的独立物理机 | 见 §1 |
| 状态 | 无旧 `device-runtime` 服务、无 `/opt/ai-device-client`、无 `ai-device-client-management` | 否则首装路径测不干净 |
| 账户 | 至少一个普通非管理员 GUI 用户可以真实登录 | LaunchAgent 是 GUI 域，必须真的登录会话 |
| 权限 | 操作者具备 sudo，且**每次使用 sudo 需当次确认** | 见 §6 |
| 网络 | 可离线 | 验证“不联网装依赖”是验收项 |

### 2.2 明确不作为环境的东西

- **不**使用当前开发机。
- **不**使用 `ai-device-wt-macos-arms` 所对应的设备或工作树。
- **不**使用任何承载真实业务的机器。

### 2.3 快照策略

每个场景开始前恢复 VM 快照。这不是为了省事，而是因为安装验证会写入机器级单例路径，
失败后残留状态会污染下一个场景——而这正是本项目历史上多次误判的来源。

## 3. 被测制品

### 3.1 当前制品与源码不一致

现有 `build/client-native/mac-final-*` 目录下的制品**不包含本轮全部源码**。开始验证前必须：

1. 从当前 worktree 重新构建 tree / wheels / PKG
2. 记录每个制品的 SHA256
3. 在验证报告中写清“本次验证对应的 commit 与制品哈希”

用旧制品验证当前代码，等于什么都没验证。

### 3.2 需要先解除的一道门禁

当前 PKG 是 inspection-only：`PREINSTALL` 直接 `exit 1`，`Distribution.xml` 里
`installation-check` 调用 `rejectInspection()`。真实安装验证**必须**使用一个
允许安装的构建。

这带来一个必须先做的决定：

> 是否新增一个**专用的验证构建模式**（例如 `--verification` 参数），
> 使 PKG 可安装，但产物明确标记为非发布件？

建议**做**，理由：
- 直接改 inspection-only 常量会让“当前默认产物不可安装”这个安全属性消失；
- 专用模式可以把“允许安装”限定在显式参数下，默认行为不变；
- 需要在产物文件名、`Distribution.xml` 的描述、以及 `pkgutil --payload-files`
  可见的元数据里都带标记，避免验证包被误当发布包分发。

#### 与残留检测合并实施

真实发布版的 `preinstall` 本来就要重写（现在是 `exit 1`），所以**残留检测应作为
这次重写的一部分，不单独做**。先做一个能跑但装不了的 preinstall 再改一次，
是白折腾。

#### preinstall 的残留检测：用拒绝代替清理

**方向已定：cleanup 不做，改用「检测到 stage 残留就拒绝安装」。**
但第五轮评审推翻了“代价很低”的推理，下面按纠正后的事实重写。

##### 为什么不用清理

cleanup 意味着再次回到四轮评审都未做对的运行时序控制（提交回执、旧树身份证明、
生命周期串行化）。而从 `bom(5)` 可知 Installer 不会清理 BOM 外的残留，
所以拒绝至少能阻止混树，且实现简单得多。

##### 已纠正的事实：每次安装都会留残留

早期版本的错误论证是「首次安装与 A→B 升级后 stage 路径都会消失」，
依据是“路径不同就走 EXCL”。**这是错的**。

commit 选择分支看的是 **program 是否存在**，不是 stage 路径是否新
（`client-macos-program-commit.h:74-79`）。所以：

| 次序 | program | 分支 | stage 结果 |
|---|---|---|---|
| 首次安装 A | 不存在 | `RENAME_EXCL` | 路径消失 |
| A→B 升级 | **存在** | **`RENAME_SWAP`** | **留 A 树** |
| 同版重装 B #1 | 存在 | `RENAME_SWAP` | 需先清残留 |

##### 残留拒绝的真实代价

| 操作 | 结果 |
|---|---|
| 装 A | 成功 |
| 升 B | 成功，**B stage 留 A 树** |
| 重装 B | **第 1 次就被拒绝** |
| 删残留后重装 | 成功，**再留旧树** |
| 再重装 | 又被拒 |

**不是“偶尔删一次”，而是“每次重装都要删”。** 这大幅削弱了拒绝方案的吸引力。

##### 三条路（**暂不选定，等 C4 证实后再定**）

| 方向 | 代价 | 风险 |
|---|---|---|
| **A. 接受残留拒绝** | 每次重装前人工 `sudo rm -rf` | 可用性差，但无静默错误 |
| **B. 实现 cleanup** | 回到四轮未做对的时序控制 | 已证明难做对 |
| **C. commit 自行移到 debris** | SWAP 后 `rename` 旧树到固定回收目录 | 仍需 root 删除，但不阻塞安装 |

方向 C 与四轮失败的清理的区别：它**不需要判断“该删哪棵树”**，只做一个确定性
`rename(stage → debris/<timestamp>)`——旧树位置固定（刚被 swap 出来），
不涉及路径别名检查。失败不回滚、不重试、不推断。

#### 为何暂不选定

上述三条路都在回答同一个问题：“stage 里混了旧文件怎么办”。但这个问题
**是否真实存在，取决于 C4**（Installer 是否保留 BOM 外文件），而 C4 目前只有
`bom(5)` 的一句话，**不足以推出结论**。

评审还发现 `pkgbuild(1)` 里 `BundleOverwriteAction=upgrade` 会整体替换 bundle
并删除新包不存在的旧路径。如果本包的 stage 目录也按这种语义处理，那么
**混树根本不会发生**，三条路全部多余。

因此：

```
C4 成立（旧文件保留）
  ├─ 是 → 混树真实存在 → 才需要选 A/B/C
  └─ 否 → 混树不存在 → 三条路均作废，路径唯一化也已足够
```

在 C4 确认前就选方向，等于为一个可能不存在的问题写代码。这正是前四轮
反复出问题的模式——先做机制，再发现前提不成立。

**当前立场：保留三条路的记录，不实施其中任何一条。**

##### 证实 C4 的最短路径

不需要完整验证流程，S5 一个场景就够：

```
1. 装 A，确认 /opt/ai-device-client-stage-<A> 消失
2. 升 B（program 存在，走 SWAP）
3. 检查 /opt/ai-device-client-stage-<B> 的内容
   ├─ 含 A 的文件 → C4 成立，混树真实
   └─ 为空       → C4 不成立，Installer 整体替换了目录
```

这一步只需要一台 arm64 机器与一个可安装的包，**不需要完整的 14 场景验收**。
它应当成为真实环境验证的第一个动作，排在 S1 之前——因为它决定后续
所有设计是否成立。

##### 实现约束（若 C4 成立且最终选 A 或 C）

1. **必须覆盖悬空符号链接。** `[ -e ]` 对悬空 symlink 返回 false：
   ```sh
   if [ -e "$STAGE" ] || [ -L "$STAGE" ]; then ... exit 1; fi
   ```
2. **位置必须在 preinstall。** postinstall 时 payload 已写入，无法区分“本来就在”
   和“刚写进去的”。
3. **错误信息要可操作**：给出具体路径、可能成因、以及需要人工执行的命令。

##### cleanup 代码的去留

**保持禁用，不修复，不删除。** 若选方向 C，它是另一个机制，不复用现有 cleanup
原语（后者包含 fd 相对遍历与路径身份校验，正是四轮出问题的部分）。

##### 对验收口径的影响

C1（旧 stage 树被清除）仍为**未实现**。但 C2 能否由“路径唯一化 + 残留拒绝”
满足，**现在取决于方向选择**：

- 选 A：C2 满足，但每次重装需人工干预
- 选 C：C2 满足，且无需人工干预
- 选 B：回到原问题

在方向选定且实施前，**C2 仍为部分满足，阶段结论仍卡住**。

##### 评审发现的其他问题（见 §9.7）

本轮评审还指出 C4（Installer 不删除 BOM 外文件）与 C5（preinstall 时序）
**均无法只读定论**，以及 C1 的“路径唯一”实为“前缀唯一”。
这些都已记录在 §9.7。

## 4. 验证场景

按需求 §11 的 25 项矩阵筛选出**只能在真实环境验证**的部分，按依赖顺序排列。
每项都要独立记录结果，不合并成“整体通过”。

### S1 — 干净机首次安装（未配置）

| 项 | 内容 |
|---|---|
| 前置 | 全新快照，无任何 ai-device 残留 |
| 操作 | `sudo installer -pkg <pkg> -target /` |
| 期望 | 安装成功；`/opt/ai-device-client` 存在且内容与 tree 清单一致；**不启动服务**；无配置时状态为“待配置”而非循环重启 |
| 关键核对 | postinstall 是否真的执行了 commit；`/opt/ai-device-client-stage` 的最终状态；`install-status` 文件内容 |
| 已知未验证点 | postinstall 从未执行过，本项是它第一次运行 |

### S2 — 首次配置

| 项 | 内容 |
|---|---|
| 操作 | 以指定普通用户身份完成配置（运行用户、身份、URL、凭证） |
| 期望 | LaunchAgent 加载；服务在**该普通用户**的 GUI 域运行；`ps -o user` 确认不是 root |
| 关键核对 | HOME 与 program 归属正确；凭证不进入 stdout/stderr/日志 |
| 对应验收 | §11「Mac root 安装程序」 |

### S3 — 生命周期

| 项 | 内容 |
|---|---|
| 操作 | 用户登出 → 重新登录；可选重启 |
| 期望 | 登出后服务停止；重新登录后启动；不要求未登录运行 |
| 关键核对 | `launchctl print gui/<uid>/local.ai-device.client` 在各阶段的状态 |

### S4 — 同版本重装

| 项 | 内容 |
|---|---|
| 操作 | 对已安装环境再次安装同版本包 |
| 期望 | 程序可修复；配置/身份/状态不变；不重复创建服务；不产生第二个实例 |
| 关键核对 | RENAME_SWAP 后 stage 的残留内容；debris 是否按设计处理 |

### S5 — A→B 升级（空闲）

| 项 | 内容 |
|---|---|
| 前置 | 在 A 版本上完成配置并确保实例空闲 |
| 操作 | 通过 Upgrade 入口执行 |
| 期望 | 版本实际变为 B；配置与日志保留；ready 精确匹配新的 build_id |
| 关键核对 | 阶段码输出；`AI_DEVICE_UPGRADE_READY_EXACT_V1` 是否出现 |

### S6 — 忙时拒绝升级

| 项 | 内容 |
|---|---|
| 前置 | 在前台或后台任务执行中触发升级 |
| 期望 | 拒绝升级；任务继续；新请求准入正常；不排队等待 |
| 关键核对 | 退出码与阶段码；任务未中断 |

### S7 — 忙拒绝后重试

| 项 | 内容 |
|---|---|
| 操作 | S6 之后，待任务结束再次升级 |
| 期望 | 同一路径可成功，不被旧意图永久阻塞 |

### S8 — 停止失败 / 状态未知

| 项 | 内容 |
|---|---|
| 操作 | 制造旧实例无法正常退出的情形（见 §5 故障注入） |
| 期望 | 不覆盖运行程序；不强杀；报告为 UNKNOWN 而非成功 |

### S9 — 损坏修复

| 项 | 内容 |
|---|---|
| 操作 | 破坏已安装的 `/opt/ai-device-client`（例如删掉入口或解释器） |
| 期望 | 无需执行旧升级器即可重装修复；确认服务不在运行后处理 |

### S10 — 普通卸载

| 项 | 内容 |
|---|---|
| 操作 | 按文档卸载 |
| 期望 | 服务移除；**配置与业务数据保留** |

### S11 — 错平台 / 损坏包

| 项 | 内容 |
|---|---|
| 操作 | 尝试安装 x86_64 包、篡改后的包、低于最低系统版本的包 |
| 期望 | 尽量在停机前拒绝；不改配置身份；错误信息明确 |

### S12 — 并发安装

| 项 | 内容 |
|---|---|
| 操作 | 两个 installer 同时执行（见 §5） |
| 期望 | 无双进程、无重复服务 |
| **当前预期** | **大概率失败** —— commit 明确不取管理锁，并发安装器互斥未实现 |

### S13 — 旧布局冲突

| 项 | 内容 |
|---|---|
| 前置 | 在测试机上故意创建 `com.device-runtime.macmini` 之类的旧服务定义 |
| 操作 | 尝试首次安装/注册 |
| 期望 | **拒绝**并给出明确说明；不覆盖；不启动第二个同身份客户端 |
| 备注 | 这一项可以在本机**只读地**验证拒绝分支，因为拒绝不产生副作用 |

### S14 — 中心 / MCP 回归

| 项 | 内容 |
|---|---|
| 期望 | 客户端清理不导致原部署/启动能力失效 |
| 备注 | 与 macOS 安装无强依赖，可与其他工作并行 |

## 5. 故障注入方式

只列**不改变生产代码**的手段。任何需要改代码才能注入的故障，单独提请评审。

| 目标 | 手段 |
|---|---|
| 旧实例不退出 | 让实例持有租约期间持续有任务；或临时把 ready 应答替换为不响应（需在隔离环境内） |
| 安装器中断 | 在 postinstall 执行中途 `kill -9` installer（此操作用 sudo，需当次确认） |
| 并发安装 | 同一终端并行起两个 `installer` 进程 |
| 损坏包 | 复制 PKG 后修改 BOM 或 payload 的一个字节 |
| 磁盘不足 | 挂载一个小容量 sparse image 作为目标（避免动真实磁盘） |
| 权限不足 | 用非管理员用户执行 installer |

**禁止**使用的手段：
- `pkill -f` 之类范围不可控的杀进程
- 删除或重建锁文件（无法证明旧 inode 持有者已退出）
- 对本机任何真实服务执行 stop/restart

## 6. 停止条件与安全边界

### 6.1 立即停止并报告的条件

- 任何一步影响了**当前开发机**上的 `com.device-runtime.macmini` 服务
- 出现无法用快照回滚的状态残留
- 需要超出已授权范围的 sudo 操作
- 测试机上有未知的其他客户端实例

### 6.2 sudo 使用规则

本方案涉及的所有 sudo 操作必须**逐条列给用户、获得当次确认后执行**。不接受
“验证期间整体授权 sudo”这种模糊形式。每次调用前说明：要执行什么、改哪个路径、
如何回滚。

### 6.3 不做什么

- 不 push、不部署、不操作任何真实服务
- 不删除任何临时目录、缓存、制品（沿用既有全保留要求）
- 不对中心/MCP 做变更

## 7. 证据要求

每个场景产出：

1. `version` / `build_id` / 制品 SHA256
2. 平台与系统版本
3. 实际执行的完整命令
4. 退出码与关键输出（**不含凭证**）
5. 关键路径的实际状态（`ls -la`、`launchctl print` 片段）
6. 结论：通过 / 失败 / 未得出
7. 未测项说明

证据存放在独立目录，命名带时间戳与场景编号，不复用旧制品名称。

## 8. 建议的执行顺序

### 8.0 第零步：先判 C4

**在跑任何场景之前，先确认 C4**（Installer 是否保留 stage 里不在 payload 中的文件）。
理由：它决定混树风险是否存在，进而决定 §3.2 三条路是否需要。

```
装 A → 升 B → 检查 /opt/ai-device-client-stage-<B>
  含 A 文件 → C4 成立 → 混树真实，需选残留方向
  为空       → C4 不成立 → 三条路作废，路径唯一化已足够
```

代价很小（一次安装 + 一次升级 + 一条 `ls`），但它能作废或确认一大批设计讨论。

如果 C4 不成立，本目录下与“残留”相关的所有内容都降为历史记录。

### 8.1 其余场景的顺序

不是按 S1…S14 顺序，而是按“能多快得到有效反馈”排序：

```
第一轮（最小可行，含 C4）
  C4 判定          ← 装 A → 升 B → 看 B 的 stage
  S1 首次安装        ← postinstall 第一次真跑，信息量最大
  S2 首次配置
  S3 生命周期

第二轮（升级路径）
  S5 A→B 升级        ← 同时是 C4 的补充证据
  S4 同版本重装（装 A → 升 B → 重装 B）
  S10 卸载

第三轮（失败与边界）
  S6 / S7 忙拒绝
  S8 停止失败
  S9 损坏修复
  S11 错平台

第四轮（已知缺口，预期失败）
  S12 并发安装       ← 大概率失败，用来确认缺口真实存在
  S13 旧布局冲突
```

先做第一轮。如果 S1 就失败（很可能，因为 postinstall 从没跑过），
后续场景全部无意义，应停下来修。

## 9. 验收口径：「未实现」与「不适用」

### 9.1 判定规则

> **「不适用」只用于验收要求本身不再成立**（需求取消、平台无此机制）。
> **「未实现」用于要求仍然成立、但当前没有可用实现。**

cleanup 属于后者，三条事实支撑：

1. **需求侧要求未取消。** §11 要求同版重装与 A→B 升级成立；固定共享 stage 路径若不清除，
   会与下次安装的 payload 混树。该风险至今**未被证伪**。
2. **用户授权的是换方案，不是取消能力。** 即从字符串路径修补改为协调器提交回执 ＋ 旧树身份证明
   ＋ 生命周期串行化。实现至今完整保留在原生语层。
3. **代码现状是主动禁用，不是不存在。** 生产入口返回 `STAGE_CLEANUP_DISABLED_V1` 和 rc64，
   原语与测试 harness 仍可直接调用。被主动关掉的功能是推迟，不是移除。

标「不适用」等于悄悄把验收范围缩小一格，而这正是本项目反复出问题的方式。

### 9.2 清理缺口：独立能力项

不把清理塞进各场景重复失败，抽成独立能力项：

| 项 | 内容 | 口径 |
|---|---|---|
| **C1** | 升级/重装后旧 stage 树被清除 | **未实现，且决定不做**。由“残留检测 + 拒绝安装”替代（§3.2） |
| **C2** | 旧树不清除时不污染下次 payload | **已由两个机制共同满足**：路径唯一化（已实施）+ 残留拒绝（待实施） |

同一缺口只记一次。否则它会在 S4、S5、S10 里各失败一遍，把 1 个缺口数成 3 个。

#### C2 的满足方式（第五轮评审后再次修正）

这里已经错过两次，记录清楚：

| 版本 | 当时的说法 | 为何错 |
|---|---|---|
| 第 1 次 | 路径唯一化即满足 | 同版重装仍混树 |
| 第 2 次 | 路径唯一化 + 残留拒绝，且拒绝仅触发于第 2 次重装 | A→B 走 SWAP，升级后即留残留，**第 1 次重装就被拒** |
| 现在 | 取决于 §3.2 三条路的选择 | — |

正确的序列表：

| 安装序列 | program | 分支 | stage 写入前 | 结果 |
|---|---|---|---|---|
| 首次安装 A | 不存在 | `RENAME_EXCL` | 新目录 | ✅ 干净 |
| A→B 升级 | 存在 | **`RENAME_SWAP`** | 新目录 | ✅ 不混树，**但留 A 树** |
| 同版重装 B #1 | 存在 | `RENAME_SWAP` | **含 A 树** | ❌ 需先清残留 |

因此 **C2 不是“已满足”，也不是“落地后即满足”**。它取决于 **C4 是否成立**：

```
C4 不成立 → 混树不发生 → C2 已由路径唯一化满足
C4 成立   → 混树真实 → 需在 A/B/C 中选择后才可能满足
```

完整推导见 `doc/client-macos-stage-path-uniquification-plan.md` §3.3。

**S4 的设计要改**：三连装不够。应先做 “装 A → 升 B → 重装 B”，
因为这才是暴露“升级后 stage 即脏”的最短序列。

### 9.3 各场景受影响情况

| 验收项 | 依赖残留检测 | 口径 |
|---|---|---|
| S10 卸载保留配置与业务数据 | 否（移除服务＋保留数据，独立路径） | **适用**，应实测通过 |
| S4 同版本重装 | 是 | **适用**；序列改为“装 A → 升 B → 重装 B”，暴露升级后即脏 |
| S5 A→B 升级 | 否（路径不同） | **适用**；同时记录 stage 是否留下 A 树（用于验证 C4） |
| S12 并发安装 | 否（锁问题，另一缺口） | **适用**，预期**失败** |

关键区分：**S4/S5 本身要测、要跑**，不能因为任何缺口就跳过整个场景。

另：S5 的附带价值变大了——它是确认 **C4（Installer 是否保留 BOM 外文件）**
的最直接机会。升 B 后检查 B 的 stage：若有 A 的残留文件，C4 成立；
若为空，C4 不成立（Installer 确实整体替换了目录），那么整个混树风险分析
需要重做。

### 9.4 对阶段结论的影响

> **存在任何「未实现」项时，macOS 阶段结论只能是「未完成交付」，不能写「通过」或「基本通过」。**

当前状态：

| 缺口 | 状态 | 是否阻塞交付 |
|---|---|---|
| C1 旧树被清除 | 未实现，**决定不做** | 先看 C4 |
| C2 不污染下次 payload | **待 C4 判定** | 先看 C4 |
| C4 Installer 不删 BOM 外文件 | **未证实** | **阻塞** —— §8.0 第一步就要确认 |
| C5 preinstall 时序 | **未证实** | 阻塞，但只影响残留拒绝方案 |

**当前唯一真正的阻塞是 C4。** 在它确认前，对其他项做决定都是空转：

- C4 不成立 → 混树不存在，C1/C2 只剩磁盘空间问题，不阻塞交付
- C4 成立 → 需选定残留方向，C2 才可能满足

在 C4 确认前，**阶段结论仍为“未完成交付”**，但原因不是代码缺口，
而是**一项关键事实尚未验证**。这是两种不同的阻塞，不应混为一谈。

### 9.5 其余预期失败项

以下项在现有代码下**预期不通过**，不应在验证后当作「新发现的 bug」：

| 项 | 预期失败原因 |
|---|---|
| S12 并发安装 | commit 不取管理锁，无并发互斥 |
| S8 部分路径 | 锁所有权只能证「非空闲」，不能证本进程持有 |
| 祖先/后代进程 | 只杀直接 helper，不杀后代 |

单列这些，是为了让验证结果可解释：**失败不等于回归，可能是已知未实现**。

### 9.5.1 已知缺口：per-pid stage 残留无回收

存在第二套 stage 机制，与 PKG 安装路径独立：

| | PKG 安装路径 | 原生安装器发布路径 |
|---|---|---|
| 入口 | postinstall → commit 动词 | `installer-inspection` 的 `upgrade-registered-program` / `repair-registered-program` |
| 发布函数 | `commit_staged_program` | `publish_first_program` / `publish_registered_target` |
| stage 路径 | `/opt/ai-device-client-stage`（固定） | `/opt/.ai-device-client-stage-<pid>`（per-pid） |
| 旧树去向 | 留回固定 stage | 留回 `.…-<pid>` |

**调用链已核实**：

```
publish_first_program ← first-entry.h:15 ← installer.m:19
publish_registered_target ← registered-upgrade.h:92 / repair-entry.h:163 ← installer.m:40
```

`installer.m:52-58` 的动词分派生效，且该二进制已编译进制品
（`.../expanded/Scripts/installer-inspection`）。

**准确表述**：这是**活的生产代码路径**，不是实验机制；当前仅被 inspection 门禁
（preinstall `exit 1`）挡住无法执行。上一版写成「未接入生产」是错的，已纠正。

**缺口内容**：`copyfile` 失败或校验失败时，`fail("...; stage retained")` 会保留
整棵 `.…-<pid>` 树。全仓搜索 `gc-stage` / `prune` / `stale stage` **零命中**，
没有任何回收机制。固定 stage 每版本留一个，而 per-pid 每次失败留一份完整体积，
量级不可预测。

**与本验证方案的关系（重要）**：

> 该路径与 inspection 门禁**直接相关**。§3.2 要求为验证准备可安装的构建——
> 一旦门禁解除，`installer-inspection` 及其动词分派即成为可达路径。

因此它不是「未来缺口」，而是**解除门禁后即暴露的当前缺口**。本验证方案不把它列入
S1–S14 场景（因为本次验证的主路径是 postinstall → commit），但必须在验证报告中
明确标注：“本次未覆盖 installer-inspection 的发布路径及其残留”。

**本机现状**：`/opt` 下无任何 ai-device 残留，基线干净。

**建议**：在 §3.2 的验证构建模式评审中，一并决定是否同时限制或禁用
`installer-inspection` 的 per-pid 发布路径，避免验证期间引入不可控的残留。

### 9.6 第五轮评审结果（2026-11-05）

评审会话 `ses-14548`，命题式限定评审，一轮。基线 `17fc129`。

#### 反例 1：C1 路径唯一性是假的

**命题**：不同 `(version, build_id)` 产生不同路径。

**反例**：两个 build_id 前 12 位 hex 相同（如 `sha256:aaaaaaaaaaaa…000` 与
`sha256:aaaaaaaaaaaa…111`），路径完全相同。

**关键**：不需要真实 SHA-256 碰撞，**截断本身就构成反例**。

**修正**：命题应改为「**前缀**不同的组合产生不同路径」。48 bit 碰撞在单机场景
可忽略，但表述必须准确。

另：`build_id` 仅覆盖 Python 源码，所以「不同完整包必有不同 stage」不成立。

#### 反例 2（致命）：A→B 升级走的是 SWAP，不是 EXCL

**命题**：任务书中“首次安装和 A→B 升级后都走 EXCL”的论断。

**实际**：分支依据是 **program 是否存在**，不是 stage 路径是否新：

```c
// client-macos-program-commit.h:74-79
if (!lstat(program, &program_info)) { flags = RENAME_SWAP; }
else if (errno == ENOENT)            { flags = RENAME_EXCL; }
```

A→B 升级时 program 已存在（载着 A），所以走 **SWAP**，B 的 stage 留下 A 树。

**后果**：推翻「残留拒绝不会锁死重装」的全部推理。一次升级后，该版本的同版
重装**从第 1 次就被拒绝**，而不是第 2 次。

**这是作者的事实错误，不是设计被证伪。** 已在 §3.2 与 stage 方案 §2/§3.3 纠正。

#### 反例 3：C7 推不出来

C1–C6 成立**不能**推出 C7（写入前不含外来文件），因为命题清单漏了
「stage 存在时必须拒绝」这个前提本身。它属于外部策略，不是由前六条推出的结论。

**修正**：C7 应改写为「若 C1–C6 成立 **且残留拒绝已实施**，则非并发序列下
payload 写入前目录为空」。

#### 未能证伪但也不能证的

| 命题 | 评审结论 |
|---|---|
| C2（EXCL 后路径消失） | 未发现反例；但不能把 program 已存在的 A→B 归入 EXCL |
| C3（SWAP 后 stage 是旧 program 树） | 未发现代码反例；未执行真实 rename |
| **C4（Installer 不删 BOM 外文件）** | **无法只读定论**。`bom(5)` 不足以推出“必然保留”；
`pkgbuild(1)` 还提到 `BundleOverwriteAction=upgrade` 会整体替换 bundle 并删除
新包不存在的旧路径，`update` 才保留。不能据此断定本包 stage 会被替换，但
C4 证据链**不够强** |
| **C5（preinstall 在 payload 前执行）** | **无法只读定论**。手册确认脚本被识别为 preinstall，
但不足以证明时序；当前 preinstall 又无条件退出 |
| C6（无其他写入方） | 默认产品路径下未发现反例；per-pid 路径名称不同。
未做全盘第三方枚举 |

#### 对验收的影响

- **C4 未证实** 意味着“混树”这个风险本身都未经权威确认。S4 三连装测试
  的第一价值变成了**确认 C4 是否成立**，而不是验证拒绝逻辑
- **C5 未证实** 意味着 preinstall 检测的时序基础尚不成立
- 两者都需要**真机安装**才能定论——这又把问题推回到“没有测试环境”这个硬阻塞

#### 并发不在保证范围

评审明确：即使两个 preinstall 都观察到不存在，也可能在检查后、写入前竞争。
在未加入串行化前，**C7 不能无条件推广到并发序列**。S12 仍为预期失败。

### 9.7 观察项：cleanup 禁用后的真实残留

cleanup 禁用后，S4/S5 会**真实地**在磁盘上留下旧 stage 内容。这必须作为明确观察项
写进证据，不作为忽略项。理由：它同时是 C1 的证据，也是「下次安装实际会发生什么」的
第一手材料——可能比任何静态评审结论都有用。

执行 S4/S5 后应记录：残留路径、文件数量、与本次 tree 清单的重叠情况。
